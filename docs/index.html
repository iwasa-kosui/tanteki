文書の種類ごとに、必要な情報を検査する Skill

PRD、ADR、Design Doc、Runbook。
文書の種類ごとに、書くべき情報と書くべきではない情報が違います。

02 / DOCUMENT TYPES

文書の種類ごとに、書くべき情報は違う

規定は種類ごとに定義されていて、依頼の内容から該当する1つを選びます。

文書の種類ごとの規定
文書の種類書くべき情報書くべきではない情報
PRD要求・優先度・根拠・制約・検証方法進捗報告・課題IDの台帳
Design Doc背景・目標と非目標・設計・代替案・影響・リスク・未解決点進捗報告・課題IDの台帳
ADR背景・決定・代替案と理由・結果・状態詳細設計・実装の進捗・作業チケットの管理
Runbook前提・検知・手順・確認・停止条件・連絡先事故の原因分析・作業の進捗
調査報告方法・対象・観察・解釈・限界・示唆一人の発言からの市場全体の断定

文書の種類は7つのカテゴリに分かれています。依頼の内容から該当する種類を1つ選び、その規定だけを読みます。

03 / HOW IT WORKS

構成を検査してから、本文を書く

01

文書の種類と読者を決める

文書の種類を決めると、読者と、その種類で書くべき情報が決まります。節ごとの問いと根拠を整理します。

02

構成を検査する

構成が合格するまで本文を書きません。検査していない構成を、合格済みとして扱いません。

03

本文を検査する

事実・条件・例外を原資料と照合し、textlint も通します。原資料にない事実や数値は書きません。

構成と本文のそれぞれで、初稿・修正・能力帯の昇格の3回までを上限とし、1つの文書で最大6回に収めます。満たせなければ、残る問題を明記して草稿として返します。

04 / GET STARTED

インストールして使う

使っているエージェントに追加して、
読者と目的を添えて依頼します。

1

スキルを入れる

GitHub CLI 2.90以降と
Node.js 22以降が必要です。

gh skills install iwasa-kosui/tanteki tanteki --scope user

ターミナルで実行します。文書検査の依存関係は、初回利用時にエージェントが npm ci で導入します。公式のインストール手順 ↗

2

文書を渡す

新しいセッションを開き、
依頼文と草稿を渡します。

依頼文の例
tanteki を使って、この設計書を開発者向けに短く推敲して。
実現方式と不採用案の理由、制約、例外は残して。

（ここに草稿を貼る）

新規の執筆も依頼できます。原資料と、未決定の内容を添えてください。

PRD（製品要求書）、設計書、ADR（設計判断の記録）、運用手順、調査報告などに。文書ごとの使い分け ↗

05 / EVIDENCE

確認できた問題と、保存した記録

「スキルなし」とした20件のうち8件に文章検査の指摘を返し、そのうち6件には tanteki 独自の規則が含まれていました。このため、生成後の文書をスキル非適用の結果として扱えません。

実行時には CLI のスキル無効化を指定していましたが、モデルに届く指示の分離は検証していませんでした。この経路の確認も必要です。

実行系は、スキルなし側へ文章検査の指摘を返さないよう修正しました。分離を確認した条件での再測定は未実施です。

出力と判定は検証用に保存

元の本文、評価、集計値は保存しています。記録内の「スキルなし／あり」は実行時のラベルです。スキルの効果を示す資料としては使えません。
