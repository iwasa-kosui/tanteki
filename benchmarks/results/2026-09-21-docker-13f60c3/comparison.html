4.1 ファイル取込API

例:

APIは以下を実行する。

  1. 取込IDを発行する。

  2. ファイルをオブジェクトストレージへ保存する。

  3. 保存先情報を含むメッセージをキューへ登録する。

  4. 非同期処理を受け付けたことを返す。

レスポンス例:

Content-Type: application/json
{

4.2 オブジェクトストレージの保存先

保存先キーは取込IDを含め、取込単位で一意になる形式とする。

例:

imports/{import_id}/source/{filename}

実装上は、利用者が指定したファイル名をそのままパスとして利用せず、パスインジェクションを防止する。必要に応じてファイル名はメタデータとして別途保持する。

4.3 保存失敗時

オブジェクトストレージへの保存に失敗した場合は、以下の動作とする。

  • HTTP 503 Service Unavailableを返す

  • キューには登録しない

  • 取込処理を失敗として記録する

  • クライアントが再試行可能なレスポンスにする

レスポンス例:

503 Service Unavailable
{
  "error": "file_storage_unavailable"
}

保存が成功したか不明なタイムアウトの場合は、同一取込IDまたは冪等性キーを利用して重複ファイルを作らない設計を検討する。

4.4 キュー登録メッセージ

キューにはファイル本体を載せず、保存先を特定するための情報だけを登録する。

例:

{
  "import_id": "...",
  "object_key": "imports/.../source/file.csv",
  "content_type": "text/csv",
  "size_bytes": 10485760,
  "created_at": "2026-09-20T00:00:00Z"
}

メッセージには認証情報や一時URLを直接含めず、ワーカーが適切な権限でオブジェクトを取得する。

5. キュー登録失敗時

オブジェクトストレージへの保存後、キュー登録に失敗した場合の回復方法は未決定である。この状態では、ストレージ上にファイルが存在するがワーカーが処理できない孤児データが発生し得る。

実装時点では、少なくとも以下を記録する。

  • 取込ID

  • オブジェクトキー

  • キュー登録の失敗理由

  • リクエストID／トレースID

  • 再処理対象であることを示すステータス

今後の決定候補:

  • DBに取込状態を保存し、未登録状態を定期的に再送する

  • Outboxパターンを利用する

  • キュー登録を同期的にリトライする

  • 運用者が再送できる管理機能を設ける

回復方法が決定するまでは、キュー登録失敗を成功扱いにせず、監視で検知できる状態にする。

6. ワーカー処理

ワーカーはキューからメッセージを受け取った後、以下を実行する。

  1. メッセージから取込IDとオブジェクトキーを取得する。

  2. オブジェクトストレージからファイルを読み込む。

  3. ファイル形式・サイズなどの入力検証を行う。

  4. ファイルを解析する。

  5. 解析結果をDBへ保存する。

  6. 処理状態を完了に更新する。

  7. 成功時にキューのメッセージをackする。

解析またはDB保存に失敗した場合は、メッセージを即時ackせず、キューの再配信方針に従う。処理の重複に備え、import_idをキーとして解析結果の保存を冪等にする。

7. 状態管理

取込状態の例:

received
storage_succeeded
queued

completed

状態更新は、API・ワーカー・運用処理のどこで更新したか追跡できるようにする。特に queue_registration_failed は、後続の回復処理対象として識別可能にする。

8. DB保存

解析結果は取込IDと紐付けて保存する。

最低限必要な項目:

  • import_id

  • 解析結果

  • 処理ステータス

  • エラー情報

  • 作成日時

  • 更新日時

同じメッセージが再配信されても、同一取込IDの結果が重複登録されないように、一意制約またはupsertを利用する。

9. エラー処理・監視

監視対象:

  • オブジェクトストレージ保存失敗数

  • キュー登録失敗数

  • キュー滞留数・滞留時間

  • ワーカー処理失敗数

  • 再試行数

  • queue_registration_failed の件数

  • 解析完了までの所要時間

ログには取込ID、リクエストID、オブジェクトキー、エラー分類を含める。ただし、ファイル本体や機密情報はログに出力しない。

解析結果はAPIリクエスト中には返却せず、受付後にバックグラウンドで生成する。そのため、利用者が結果を確認できるまでの時間が従来より遅くなる。

結果提示方法は別途決定するが、当面は取込IDを返し、ステータス確認APIなどで処理状態を取得できる構成を前提とする。

背景

ファイル取込をAPI処理と解析処理に分離する。APIはファイル本体をキューへ載せず、オブジェクトストレージに保存したファイルの保存先をキューへ登録する。ワーカーは保存先からファイルを読み、解析結果をDBへ保存する。

目的と非目標

目的

  • APIと解析処理を非同期化する。

  • キューにはファイル本体ではなく保存先を渡す。

  • 解析結果をDBに保存する。

  • オブジェクトストレージへの保存失敗をAPIの503として返す。

非目標

  • キューへの登録失敗時の回復方法をこの文書で決定する。

利点

  • APIと解析処理を分離できる。

負担と制約

  • 利用者への解析結果の提示は、非同期化により遅れる。

  • API、オブジェクトストレージ、キュー、ワーカー、DBの連携が必要になる。

  • キューへの登録失敗時の回復方法が決まるまで、失敗時の動作を確定できない。

未解決点

キューへの登録に失敗した場合の回復方法を決定する必要がある。少なくとも、APIの応答、オブジェクトストレージに保存済みのファイルの扱い、再試行の方法を決める。

システムの到達範囲

実装時は、APIの保存処理、保存先のキュー登録、ワーカーの取得・解析・DB保存を順に実装する。保存失敗時の503とキュー未登録を確認する。キュー登録失敗時の回復方法が未決定のため、その動作確認は決定後に行う。

1. 概要

  • 解析結果はDBへ保存する

  1. 取込IDを発行する

  2. imports または同等の管理テーブルへ受付情報を保存する

  3. オブジェクトストレージへファイルを保存する

  4. 保存先情報をキューへ登録する

  "bucket": "file-imports",

確定事項:

  • APIは 503 Service Unavailable を返す

  • キューには登録しない

処理方針:

  1. ファイル保存を実行する

  2. 保存が失敗した場合はキュー登録処理を実行しない

  3. 必要に応じて、作成済みの受付レコードを失敗状態へ更新する

  4. 503 とエラーコードを返す

レスポンス例:

{
  "code": "OBJECT_STORAGE_UNAVAILABLE",
  "message": "ファイルを保存できませんでした。時間をおいて再試行してください。"
}
5.2 キューへの登録失敗

回復方法は未決定である。実装では以下を暫定方針とする。

  • キュー登録失敗を検知し、受付レコードを queue_registration_failed などの状態へ更新する

  • APIは成功扱いにせず、運用上再処理可能なエラーとして扱う

  • 再送を自動で行うか、管理者・バッチによる再送とするかは別途決定する

  • 再送時に同一ファイルが二重処理されても結果が壊れないよう、ワーカー側で冪等性を確保する

キュー登録失敗時のAPIレスポンスコード、再送回数、再送間隔、保存済みファイルの保持期間は未確定事項として残す。実装前に決定すること。

5.3 ワーカーでの読み込み失敗

  • 一時的なオブジェクトストレージ障害は、キューの再試行機能またはリトライで再実行する

  • ファイルが存在しないなど恒久的なエラーは、取込状態を失敗に更新し、無限リトライを防止する

  • 再試行回数を超えたメッセージは、既存のDLQ等の運用方針に従う

5.4 解析失敗

  • 解析不能なファイルは取込状態を failed に更新する

  • エラー理由は利用者に提示可能な情報と、ログにのみ出す内部情報を分離する

  • 同一メッセージの再実行で重複した解析結果を作らない

6. 状態管理

取込単位で、少なくとも以下の状態を管理する。

状態意味
acceptedAPIが受付を完了した
storedオブジェクトストレージへの保存が完了した
queuedキュー登録が完了した
processingワーカーが解析中
completed解析結果をDBへ保存した
failed解析または回復不能な処理に失敗した
queue_registration_failedファイル保存後、キュー登録に失敗した

状態遷移例:

accepted → stored → queued → processing → completed
                    │           │
                    │           └→ failed
                    └→ queue_registration_failed

APIの受付情報、オブジェクトストレージのキー、解析結果、エラー情報は同じ import_id で関連付ける。

7. 整合性・冪等性

オブジェクトストレージ保存とキュー登録は単一トランザクションではないため、以下の不整合が発生し得る。

  • ファイル保存成功後にキュー登録が失敗する

  • キュー登録成功後にAPI応答が失敗する

  • ワーカーが同一メッセージを複数回処理する

対策:

  • import_id を一意キーとして扱う

  • 解析結果の保存時に一意制約またはUPSERTを利用する

  • ワーカーは処理開始前・保存前に現在状態を確認する

  • キューの再配信を前提に、処理を冪等にする

  • APIの再送で同じ取込IDを再利用するか、新規取込として扱うかをAPI仕様で明確化する

キュー登録失敗の回復方法を決定する際には、Outboxパターンなど、DB上の登録情報を起点にキューへ再送できる方式を候補とする。

8. 非同期化による利用者影響

解析結果はAPIレスポンス時点では確定しない。利用者には以下のいずれかの結果確認方法を提供する。

  • GET /imports/{import_id} による状態確認

  • 完了時の通知

  • 既存画面でのポーリング

最低限、取込IDと現在状態を返し、利用者が処理中・完了・失敗を判別できるようにする。結果提示までの遅延が発生することをAPI仕様および画面仕様に明記する。

9. セキュリティ・運用

  • オブジェクトストレージは公開せず、APIとワーカーのサービスアカウントだけがアクセスできるようにする

  • キューのメッセージにファイル本体や機密情報を含めない

  • ファイル名は表示用情報として扱い、保存キーにはそのまま使用しない

  • ファイルサイズ、拡張子、Content-TypeをAPIで検証する

  • ログにはファイル本体、認証情報、機密データを出力しない

  • 保存済みファイルの削除タイミングと保持期間を別途定義する

  • キュー滞留数、ワーカー失敗数、処理時間、DLQ件数を監視する

ファイル取込の設計

背景

ファイル本体をキューへ載せる案は、10 MB のファイルがキューの 1 MB 制限を超えるため採用しない。ファイルを保存先と処理要求に分離し、API の応答後にワーカーが解析する。

目標と対象外

目標は、API で受け付けたファイルを非同期に解析し、解析結果を DB へ保存できる構成にすることである。

対象外は、キューへの登録失敗時の回復方法である。この扱いは未決定とする。

設計

処理の流れは次のとおりである。

sequenceDiagram
    participant C as クライアント
    participant A as API
    participant S as オブジェクトストレージ
    participant Q as キュー
    participant W as ワーカー
    participant D as DB

    C->>A: ファイルを送信
    A->>S: ファイル本体を保存
    S-->>A: 保存先
    A->>Q: 保存先を登録
    A-->>C: 受付結果
    W->>Q: 保存先を取得
    W->>S: ファイル本体を読み取り
    S-->>W: ファイル本体
    W->>W: 解析
    W->>D: 解析結果を保存
API

  1. API は受信したファイルをオブジェクトストレージへ保存する。

  2. 保存に成功したら、保存先をキューへ登録する。

  3. オブジェクトストレージへの保存に失敗した場合は、503 Service Unavailable を返す。この場合、キューには登録しない。

キューへの登録に失敗した場合の応答、保存済みファイルの扱い、再試行方法は未決定である。

ワーカー

  1. ワーカーはキューから保存先を取得する。

  2. 保存先からファイル本体を読み取る。

  3. ファイルを解析する。

  4. 解析結果を DB に保存する。

代替案

ファイル本体をキューへ登録する案は不採用とする。10 MB のファイルがキューの 1 MB 制限を超えるためである。保存先だけをキューへ登録する方式では、ワーカーが保存先からファイル本体を読み取れる。

影響

処理を非同期化するため、利用者が解析結果を確認できるまでの時間が長くなる。利用者への結果提示方法と、結果が確認可能になる条件は、この資料では定めない。

リスク

キュー登録に失敗すると、保存済みファイルと処理要求の対応を失う可能性がある。回復方法は未決定である。実装前に扱いを決める必要がある。

未解決点

  • キューへの登録失敗時に API が返すステータスと応答内容

  • キューへの登録失敗時に保存済みファイルを残すかどうか

  • キューへの登録を再試行する方法

  • 保存済みファイルを処理要求へ復旧する方法

  • 利用者へ解析結果を提示する方法

到達範囲

システムは、API によるファイル保存、保存先のキュー登録、ワーカーによるファイル取得・解析、解析結果の DB 保存までを対象とする。

手順は、API がファイルを受信してから、ワーカーが解析結果を DB に保存するまでを対象とする。キューへの登録失敗からの回復手順は、回復方法の決定後に追加する。

可逆性

ファイル本体をキューへ載せず、保存先をキューへ登録する方式は、ファイル本体の受け渡し方式を変更できる構成である。ただし、キューへの登録失敗時の回復方法が未決定のため、その影響を確認してから方式を見直す。

監視でキャッシュに関するエラーを検知した場合に、当番が安全に状況を確認し、必要に応じて再起動するための手順です。

重要：本手順は未完成です。 再起動コマンド、停止してよい条件、復旧確認方法、連絡先が未確定のため、現時点では本番環境で再起動を実施しないでください。

2. 監視でエラーを検知したら

  1. アラートの発生時刻、対象サービス、対象ホストまたはクラスタ、エラー内容を記録する。

  2. 同じ時間帯に、アプリケーション、データベース、ネットワークなどの障害が発生していないか確認する。

  3. キャッシュの再起動が必要かどうかを判断する。

  4. 判断に必要な情報が不足している場合、自己判断で再起動せず、所定の連絡先へ相談する。

3. 再起動前の確認

以下をすべて確認できるまで、キャッシュを停止しない。

  • ☐

    対象環境が本番環境であることを確認した

  • ☐

    対象のキャッシュサービス／インスタンスを特定した

  • ☐

    再起動による影響範囲を確認した

  • ☐

    停止してよい条件を満たしている

  • ☐

    実施予定と影響を関係者へ連絡した

  • ☐

    必要な承認を取得した

  • ☐

    再起動前のメトリクス、ログ、アラート状態を記録した

4. 再起動を実施してよい条件

この条件は未決定です。運用責任者が以下を確定してください。

  • 再起動対象となるエラーの種類・継続時間・発生回数

  • 再起動を禁止する時間帯やリリース中の扱い

  • 再起動してはいけない状況（データ障害、ネットワーク障害、依存サービス障害など）

  • 再起動前に必要な承認者

  • 再起動回数や再試行回数の上限

条件を満たさない場合、または判断できない場合は再起動せず、エスカレーションする。

  2. 関係者へ作業開始を連絡する。

  4. 停止・再起動中のログとメトリクスを確認する。

  5. エラーが継続する場合は、定められた上限を超えて再起動を繰り返さず、エスカレーションする。
