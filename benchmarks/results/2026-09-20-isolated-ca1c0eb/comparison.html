ADR: 請求書PDF生成を非同期キューで処理する

  • ステータス: 採用

  • 決定日: 2026-08-20

  • 関連: BILL-218、PR #106（作業メモ時点の進捗: 70%）

コンテキスト

請求書PDFの生成には最大45秒かかる場合があり、同期処理ではAPI接続が切れる可能性がある。同期生成を採用すると、利用者や呼び出し元が長時間レスポンスを待つことになり、タイムアウトや再送の扱いも複雑になる。

決定

請求書PDFの生成はキューに投入して非同期で処理する。APIは生成完了を待たず、受付IDを返す。受付IDを使って、後続の処理で生成状況や結果を確認できるようにする。

影響

利点

  • API接続が最大45秒維持されることによる切断リスクを避けられる。

  • PDF生成処理をワーカー側で実行でき、APIの応答性を保てる。

  • キューによる負荷平準化や処理の再実行を設計しやすい。

欠点・利用者への影響

  • API呼び出し時点ではPDFは完成していない。

  • 利用者は、PDFの完成まで待つか、受付IDで状態を確認する必要がある。

  • キュー滞留やワーカー障害により、完成までの時間が延びる可能性がある。

却下した選択肢

同期生成は採用しない。最大45秒かかるため、処理中に接続が切れるリスクがあるためである。

未決事項

生成処理の再試行回数の上限は未決定である。障害時の重複生成、キュー滞留、恒久的失敗の扱いを踏まえて、運用開始前に決定する必要がある。

将来の保守者向け注意

同期レスポンスでPDF本体を返す実装へ変更する場合は、接続タイムアウト、負荷特性、利用者が完成を待つ必要がある点を再評価すること。非同期処理を変更する際は、受付IDと生成状態の対応、および再試行上限の決定を併せて見直すこと。

ファイル取込 Design Doc

1. 概要

APIで受け付けたファイルをオブジェクトストレージに保存し、保存先情報をキューへ登録する。ワーカーはキューから保存先を取得し、オブジェクトストレージ上のファイルを読み込んで解析し、解析結果をDBへ保存する。

ファイル本体をキューへ登録する方式は、最大10MBのファイルがキューの1MB制限を超えるため採用しない。

2. 対象範囲

  • APIによるファイル受付

  • オブジェクトストレージへの保存

  • 保存先情報のキュー登録

  • ワーカーによるファイル取得・解析

  • 解析結果のDB保存

  • 保存失敗時のAPIエラー処理

キューへの登録失敗時の回復方法は、現時点では未決定とする。

3. 処理フロー

  1. クライアントがAPIへファイルを送信する。

  2. APIがファイルをオブジェクトストレージへ保存する。

  3. 保存に成功した場合、APIが保存先情報をキューへ登録する。

  4. APIは受付結果を返す。解析は非同期で実行する。

  5. ワーカーがキューから保存先情報を取得する。

  6. ワーカーがオブジェクトストレージからファイルを読み込む。

  7. ワーカーがファイルを解析する。

  8. ワーカーが解析結果をDBへ保存する。

4. API仕様・エラー処理

4.1 保存成功時

オブジェクトストレージへの保存後に、保存先を示すキーまたはURIをキューへ登録する。APIレスポンスには、必要に応じて受付IDなど、非同期処理の状態を追跡できる識別子を含める。

4.2 保存失敗時

オブジェクトストレージへの保存に失敗した場合は、HTTP 503を返す。この場合、キューへの登録は行わない。

保存成功後にキュー登録が失敗した場合の回復方法は未決定であるため、実装前に以下を決定する必要がある。

  • 再試行の有無と回数

  • 再試行間隔およびバックオフ方式

  • 未登録ファイルの検出方法

  • 重複登録時の扱い

  • 運用担当者による再処理方法

5. キューメッセージ

キューにはファイル本体を登録せず、少なくとも以下のメタデータを登録する。

  • 受付IDまたはファイルID

  • オブジェクトストレージ上の保存先キーまたはURI

  • 必要に応じてファイル形式、サイズ、登録日時

保存先情報だけを登録することで、キューの1MB制限を回避する。最大10MBのファイル本体はオブジェクトストレージで扱う。

6. ワーカー処理

ワーカーはキューメッセージを受信後、保存先からファイルを読み込んで解析する。解析に成功した場合は、受付IDまたはファイルIDと紐付けて解析結果をDBへ保存する。

実装時には、少なくとも以下を考慮する。

  • 保存先が存在しない場合のエラー処理

  • 一時的な読み込み失敗時の再試行

  • 同一メッセージの重複処理に対する冪等性

  • 解析失敗時の状態記録と再処理方針

  • DB保存失敗時に解析結果を失わない設計

7. 非同期処理に伴う利用者影響

解析を非同期化するため、ファイル受付から解析結果の提示までに遅延が発生する。利用者には受付完了と解析完了を区別して提示し、結果取得方法および処理状態を確認できる仕組みを用意する必要がある。

8. 未決定事項

  • キュー登録失敗後の回復方法

  • 解析処理の再試行および失敗時の扱い

  • 処理状態を取得するAPIの詳細

  • 解析完了通知の方式

  • ファイル保持期間と削除タイミング

9. 実装計画

  • 対象: DATA-64

  • 関連PR: #203

  • 今週の作業: API実装

  • 担当: 佐藤

今週は、ファイルのオブジェクトストレージ保存、保存失敗時の503応答、保存先情報のキュー登録までを実装対象とする。キュー登録失敗時の回復仕様は、別途決定後に実装へ反映する。

失敗時の動作

保存に失敗した場合、APIは503を返し、キューへ登録しない。キューへの登録に失敗した場合の回復方法は未決定である。

代替案と不採用理由

ファイル本体をキューへ載せる案は採用しない。キューの上限は1MBであり、対象ファイルの最大10MBを収容できないためである。

影響

リスク

ファイル取込 Design Doc

1. 概要

ファイル本体をAPIで受け取り、オブジェクトストレージに保存する。保存先をキューへ登録し、ワーカーが保存先からファイルを読み込んで解析する。解析結果はDBへ保存する。

ファイル本体をキューへ直接載せる方式は、キューのメッセージ上限が1MBであり、最大10MBのファイルを扱えないため採用しない。

2. 処理フロー

  1. APIがクライアントからファイルを受信する。

  2. APIがファイルをオブジェクトストレージへ保存する。

  3. 保存に成功した場合、ファイルの保存先情報をキューへ登録する。

  4. ワーカーがキューから保存先情報を取得する。

  5. ワーカーがオブジェクトストレージからファイルを読み込む。

  6. ワーカーがファイルを解析する。

  7. ワーカーが解析結果をDBへ保存する。

  8. 利用者は非同期処理の完了後に解析結果を確認する。

3. API仕様

リクエスト

  • ファイル本体をリクエストで受け取る。

  • ファイルサイズ上限は10MBとする。

  • 受付時に処理を同期完了させず、非同期処理として扱う。

成功時

オブジェクトストレージへの保存およびキュー登録が完了した場合、受付成功を返す。レスポンスには、取込処理を追跡するための取込IDを含める。

オブジェクトストレージ保存失敗時

  • HTTPステータス503を返す。

  • キューには登録しない。

  • 後続のワーカー処理を発生させない。

キュー登録失敗時

オブジェクトストレージへの保存後にキュー登録が失敗した場合の回復方法は未決定である。実装では、失敗を検知できるログおよび監視情報を残し、回復方式の決定後に差し替えられる構造にする。ストレージ上にファイルが残るため、孤児ファイルの扱いも回復方式と併せて決定する。

4. オブジェクトストレージ

保存内容

最低限、以下の情報を管理する。

  • 取込ID

  • オブジェクトキー

  • 元ファイル名

  • ファイルサイズ

  • Content-Type

  • 受付日時

オブジェクトキーには取込IDなどの一意な値を使用し、ファイル名の衝突を避ける。キューにはファイル本体ではなく、取込IDとオブジェクトキーなどの保存先情報のみを登録する。

5. キュー

メッセージには以下を含める。

  • 取込ID

  • オブジェクトストレージのバケットまたはコンテナ情報

  • オブジェクトキー

  • 必要なメタデータ

キューのメッセージサイズ制限を超えないよう、ファイル本体は含めない。

6. ワーカー

ワーカーは次の順序で処理する。

  1. キューからメッセージを取得する。

  2. 指定されたオブジェクトストレージのオブジェクトを読み込む。

  3. ファイルを解析する。

  4. 解析結果をDBへ保存する。

  5. 成功時にキューメッセージを完了扱いにする。

読み込み、解析、DB保存のいずれかに失敗した場合は、再実行可能な設計とする。解析結果の重複保存を防ぐため、取込IDをキーとした冪等性を確保する。

7. DB

取込状態を管理し、少なくとも以下の状態を記録する。

  • 受付済み

  • 保存済み

  • キュー登録済み

  • 処理中

  • 完了

  • 失敗

解析結果は取込IDと関連付けて保存する。利用者が非同期処理の進捗および結果を確認できるよう、状態取得方法は既存API設計に合わせて実装する。

8. エラー処理・運用

  • オブジェクトストレージ保存失敗は503として返し、キュー登録を行わない。

  • キュー登録失敗は検知、記録、監視できるようにする。回復処理は別途決定する。

  • ワーカー処理は再試行を考慮する。

  • 解析結果保存は冪等にする。

  • ストレージに残った未処理ファイルを特定できるよう、取込IDとログを関連付ける。

  • 非同期化により、API受付から利用者が結果を確認できるまでの時間が遅くなる。UIまたは結果取得APIでは処理中状態を提示する。

9. 実装範囲と進行状況

  • チケット: DATA-64

  • 関連PR: #203

  • 今週の実装対象: API実装

  • 担当: 佐藤

今週は、ファイル受信、オブジェクトストレージ保存、保存失敗時の503応答、およびキュー登録までを主な対象とする。キュー登録失敗時の回復方式は未決定事項として残す。

  • 保存先をキューへ登録する。

可逆性

  • キューへの登録に失敗した場合の回復方法。

  • キューへの登録失敗時に、オブジェクトストレージへ保存済みのファイルをどう扱うか。

  • 利用者へ解析結果を提示する方法と、提示までの状態管理。

ファイル取込の設計

背景と目的

ファイル本体をキューに載せず、オブジェクトストレージを介して非同期に解析する。API は取込要求を受け付け、ワーカーは保存済みファイルを解析して結果を DB に保存する。

目標と非目標

目標

  • ファイルをオブジェクトストレージへ保存する。

  • 保存先をキューへ登録する。

  • ワーカーが保存先からファイルを読み、解析結果を DB へ保存する。

非目標

  • ファイル本体をキューへ登録する。

  • キューへの登録失敗時の回復方法を決める。

設計

処理の流れ

  1. API がファイルをオブジェクトストレージへ保存する。

  2. 保存に成功したら、API が保存先をキューへ登録する。

  3. ワーカーがキューから保存先を取得する。

  4. ワーカーがオブジェクトストレージからファイルを読み取る。

  5. ワーカーが解析結果を DB へ保存する。

ファイル本体をキューへ載せる案は採用しない。キューの上限が1MBであり、対象ファイルの上限10MBを超えるためである。

保存に失敗した場合

オブジェクトストレージへの保存に失敗した場合、API は503を返し、保存先をキューへ登録しない。

キューへの登録に失敗した場合

キューへの登録失敗時の回復方法は未決定である。この設計では回復処理を定めない。

代替案と不採用理由

案判断理由
保存先をキューへ登録する採用ファイル本体をキューへ載せずに非同期化できる
ファイル本体をキューへ登録する不採用10MBのファイルが1MBの制限を超える

影響

非同期化により、利用者への解析結果の提示は遅れる。キューへの登録失敗時の回復方法が未決定であるため、登録失敗時の動作は追加の設計が必要である。

システムの到達範囲

API、オブジェクトストレージ、キュー、ワーカー、解析処理、DB を対象とする。解析結果を利用者へ提示する具体的な方法は、資料に記載がないため対象範囲に含めない。

手順の到達範囲

本書は、API からワーカーが解析結果を DB へ保存する処理の設計を扱う。API の実装手順、キューへの登録失敗時の回復手順、運用時の復旧手順は定めない。

可逆性

キューへの登録失敗時の回復方法が未決定であるため、現時点で切戻しや再処理の方法は定められない。回復方法を決定する際に、保存済みファイルの扱いを合わせて定義する必要がある。
