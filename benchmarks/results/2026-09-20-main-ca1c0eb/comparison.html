ファイル取込 Design Doc

1. 概要

ファイル取込は非同期処理として実装する。APIは受信したファイルをオブジェクトストレージへ保存し、保存先情報をキューへ登録する。ワーカーはキューから保存先情報を取得し、ファイルを読み込んで解析結果をDBへ保存する。

2. 背景・制約

  • ファイル本体をキューへ登録する方式は採用しない。

  • 10MBのファイルに対して、キューのサイズ上限が1MBであるため。

  • 非同期化により、利用者が解析結果を確認するまでの時間は従来より長くなる。

3. 処理フロー

API

  1. APIがファイルを受信する。

  2. ファイルをオブジェクトストレージへ保存する。

  3. 保存先情報をキューへ登録する。

  4. 上記が完了したら、受付済みとしてレスポンスを返す。

ワーカー

  1. キューから保存先情報を取得する。

  2. 保存先からファイル本体を読み込む。

  3. ファイルを解析する。

  4. 解析結果をDBへ保存する。

4. エラー処理

オブジェクトストレージへの保存失敗

  • APIは503を返す。

  • キューには登録しない。

キューへの登録失敗

回復方法は未決定である。実装前に、再試行、状態管理、運用による復旧などの方針を決定する。キュー登録に失敗した場合は、オブジェクトストレージ上のファイルを孤立させない仕組みも検討する。

5. データと責務

  • オブジェクトストレージ: 受信したファイル本体を保持する。

  • キュー: オブジェクトストレージ上の保存先情報を伝達する。ファイル本体は保持しない。

  • ワーカー: ファイルの取得、解析、解析結果のDB保存を担当する。

  • DB: 解析結果を保存する。

6. 実装前の確認事項

  • キューへ登録する保存先情報の形式を定義する。

  • APIの受付成功レスポンスと結果取得方法を定義する。

  • 解析中、解析完了、解析失敗などの処理状態を管理するか決定する。

  • キュー登録失敗時の回復方法を決定する。

  • 非同期処理によって結果提示が遅れることを利用者へ伝える方法を決定する。

ファイル取込 Design Doc

1. 概要

APIで受け付けたファイルをオブジェクトストレージへ保存し、保存先をキューへ登録する。ワーカーはキューから保存先を取得し、オブジェクトストレージ上のファイルを読み込んで解析し、解析結果をDBへ保存する。

2. 背景・目的

ファイル解析を非同期化し、APIのリクエスト処理と解析処理を分離する。ファイル本体をキューに載せる方式は、10MBのファイルがキューの1MB制限を超えるため採用しない。

3. 処理フロー

  1. クライアントがAPIへファイルを送信する。

  2. APIがファイルをオブジェクトストレージへ保存する。

  3. 保存に成功した場合、保存先を示す情報をキューへ登録する。

  4. APIが受付結果をクライアントへ返す。

  5. ワーカーがキューから保存先を取得する。

  6. ワーカーがオブジェクトストレージからファイルを読み込む。

  7. ワーカーがファイルを解析する。

  8. ワーカーが解析結果をDBへ保存する。

4. API仕様

成功時

  • ファイルをオブジェクトストレージへ保存する。

  • キューへ保存先を登録する。

  • 非同期処理であることを示す受付結果を返す。

  • 解析結果は受付時点では確定していないため、利用者への結果提示は後続処理となる。

オブジェクトストレージ保存失敗時

  • HTTPステータス 503 Service Unavailable を返す。

  • キューには登録しない。

  • クライアントが再試行可能なエラーとして扱えるよう、エラー内容を記録する。

キュー登録失敗時

回復方法は未決定である。保存済みオブジェクトを残し、失敗を検知できるログ・メトリクスを出力する。自動リトライ、再登録用ジョブ、定期的な未登録オブジェクト検出のいずれを採用するかは、実装開始前に決定する。

5. キューメッセージ

キューにはファイル本体を登録せず、少なくとも以下の情報を含む保存先情報を登録する。

  • オブジェクトストレージのバケットまたはコンテナ

  • オブジェクトキー

  • 取込要求を一意に識別するID

  • 必要に応じてファイル名、Content-Type、サイズなどのメタデータ

10MBのファイル本体はキューの1MB制限を超えるため、キューメッセージには含めない。

6. ワーカー実装方針

  • キューメッセージから保存先を取得する。

  • 保存先からファイルをストリーミングまたは適切な方法で読み込む。

  • 解析結果をDBへ保存する。

  • 同一メッセージの再処理に備え、取込要求IDを用いて冪等に結果を保存できるようにする。

  • オブジェクト取得失敗、解析失敗、DB保存失敗を区別して記録する。

  • 失敗時の再試行・デッドレターキューへの送付方針は、既存のキュー運用ルールに従う。ルールがない場合は、ワーカー実装前に運用担当と決定する。

7. 整合性・障害時の扱い

APIでは、オブジェクトストレージへの保存成功後にキュー登録を行う。保存に失敗した場合はキュー登録を行わない。キュー登録に失敗すると、保存済みオブジェクトが未処理のまま残る可能性がある。この状態を追跡できるよう、取込要求ID、保存先、各処理の成否をログまたは管理用データに記録する。

8. 利用者への影響

解析を非同期化するため、API受付直後には解析結果を提示できない。利用者が結果を確認する方法（ステータス照会API、通知、画面更新など）は別途設計する。少なくとも、受付状態と処理完了状態を識別できる取込要求IDを返す設計を推奨する。

9. 監視・運用

以下を監視対象とする。

  • オブジェクトストレージ保存失敗数

  • キュー登録失敗数

  • キュー滞留数・処理遅延

  • オブジェクト取得失敗数

  • 解析失敗数

  • DB保存失敗数

  • キュー登録されていない保存済みオブジェクトの件数

エラーには取込要求IDとオブジェクトキーを含め、追跡可能にする。

  1. キューへの登録失敗時の回復方法（自動リトライ、再登録ジョブ、補償処理など）。

RFC: 商品検索基盤の方式

背景・課題

商品検索が遅く、特に部分一致検索の性能改善が必要である。計測値・費用は未取得。

選択肢

  • 方式A：既存DB索引を追加

    • 利点：別サービスの運用が不要で、運用対象が増えない。

    • 制約：部分一致検索は速くならない。

  • 方式B：検索専用サービスを導入

    • 利点：部分一致検索の高速化が期待できる。

    • 制約：別サービスの運用が必要。DBから検索基盤への反映に遅延が生じる。

提案

方式Bを採用する。商品検索の主要課題である部分一致検索を改善できるためである。

検索結果は最大60秒古くなることを許容する案とする。ただし、この許容について業務側の承認は未取得であり、採用条件として別途合意が必要である。

合意が必要な事項

  1. 検索専用サービスを追加し、継続運用すること。

  2. DB更新から最大60秒の検索結果反映遅延を許容すること。

未確定事項

性能改善の計測値、運用費用、運用負荷は未評価である。方式を決定する前に、開発チームが性能・費用・運用負荷の評価方法と確認担当を決める。
