# PRD・設計・判断の書き分け

見出しを埋めるために書かない。以下は必要情報の目安であり、節の数や順序の指定ではない。読者に必要なら増やし、短文で揃うならまとめる。情報ごとに節を作ったり、項目名を見出しに列挙したりせず、[文書全体の構成](structure.md#文書全体の構成を決める)に沿ってまとめ方を決める。

| 種別 | 答える問い | 最後まで残す情報 | 他へ移す情報 |
|---|---|---|---|
| PRD | 誰の何の問題を、どの振る舞いで解決するか | 問題の根拠、利用者、要求、対象外、測定できる成功・受入条件 | クラス設計、作業分担、進捗 |
| Design Doc | どう実現し、なぜその方式か | 制約、構成、動作、採用理由、影響、未解決点 | PR/Jira一覧、完了率、今週やること |
| ADR | どの一つの判断を、なぜ採ったか | 判断の状態と日付、背景、決定、理由、結果 | 詳細設計の複製、実装進捗 |
| RFC | 誰に何の変更への合意を求めるか | 問題、提案、影響を受ける範囲、代替案、合意が必要な論点 | レビュー依頼の宛先・期限、作業台帳 |

Design Doc には、制約、構成とデータの流れ、重要な失敗時の動作、代替案と不採用理由、影響、未解決点を残す。

外部の API・仕様・測定結果や別 ADR など、判断に必要な正本は参照する。リンクだけでは読者が結論や理由を追えないなら、必要な一文を本文に残す。設計の根拠がチケットにしかない場合は、根拠となる事実を本文に抽出し、未確認の点は明記する。

## ADR の判断と結果を残す

一つの重要な判断について、背景、決定とその理由、結果を記す。判断の状態と、資料にある判断日も残す。節を分けるなら「背景」「決定」「結果」を基本にし、代替案と不採用理由は判断を理解するために必要な範囲で書く。一段落で揃うなら、見出しを増やさない。

「結果」には、採用による利点、負担、制約、その他の影響を含める。「結果と代償」とすると意味が重なる。通常の費用や運用負担を一括して「代償」と呼ばず、「DB の保存量が増える」「障害時の切替操作が必要になる」のように、何が変わるかを書く。想定される影響と、実際に確認した結果は区別する。

### 未決定事項を扱う範囲

「未決定事項」は必須の節にしない。後続の詳細設計や作業の TODO は、それを管理する設計書や作業文書へ分ける。原資料に未決定の項目があるという理由だけで、全てを ADR に転記しない。未決定事項の見出しを消して「結果」の段落に移すだけでは、役割を分けたことにならない。既存の管理先が判断に必要なら参照し、存在しない文書やリンクは作らない。

採否を左右する未確認事項は、提案中の ADR の背景や採用条件として残す。未確認事項を消して採用済みに見せない。採用済みでも、その判断が依存する仮定や、引き受けたリスク、資料で定めた再検討条件は残す。未決定事項を独立した節で説明する必要がある場合は「結果」と分け、「代償と未決定事項」のように異なる役割を束ねない。

[Nygard の原典](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)は、結果に良い影響・悪い影響・中立の影響を含める。[MADR のテンプレート](https://adr.github.io/madr/#full-template)にも、未決定事項を必須にする指定はない。上の日本語見出しと未決定事項の振り分けは、これらを踏まえた本スキルの方針である。

## 同じ題材の最小例

架空の資料: 利用者は応答が途切れると注文を再送する。新規注文 API で同じキーの再送を24時間以内は一件として扱う。同じキーで内容が異なる場合は409を返す。既存注文の変更は対象外。設計案では利用者とキーの組を一意にし、注文とキーを同じ DB トランザクションで保存する。同内容の再送には保存済みの応答を返す。別キャッシュ案は同時更新の処理が増えるため不採用。DB の保存量が増える。判断は提案段階で、24時間後のキーの扱いは未決定。

### PRD

利用者が応答を受け取れず注文を再送しても、注文を重複させない。同じ利用者が同じキー・同じ内容で24時間以内に再送した場合、注文は一件となる。同じキーで内容が異なる場合は409を返す。既存注文の変更は対象外とする。

### Design Doc

注文と再送判定用のキーを同じ DB トランザクションで保存する。利用者とキーの組を一意にし、同時に届いた再送でも注文を一件にする。24時間以内の再送は内容を比較し、同じなら保存済みの応答、異なれば409を返す。別のキャッシュへの保存は、注文との同時更新を保証する処理が増えるため採らない。24時間後のキーの扱いは未決定である。

### ADR

状態: 提案。注文の再送による重複を防ぐため、再送判定用のキーは注文と同じ DB に保存する。両者を同じトランザクションで確定するためである。別のキャッシュは同時更新を保証する処理が増えるため採らない。DB の保存量が増える。

この ADR が扱うのは保存先の判断である。24時間後のキーの扱いは上の Design Doc に残し、ADR の必須項目にはしない。保持要件が保存先の採否を左右すると分かった場合は、その条件を ADR にも残す。

## 手順や記録では残すものが違う

- Runbook: 実行者、開始条件、順序、期待結果、停止条件、復旧・連絡先。短くしても危険な操作の条件を落とさない。
- 進捗報告: 対象期間、完了、次の作業、阻害要因、判断依頼。追跡先の課題や PR を参照してよい。
- ポストモーテム: 検知時刻、影響、経過、原因と寄与要因、改善策。事実と仮説を分け、課題を参照してよい。
