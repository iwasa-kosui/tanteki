# 設計・意思決定

## Design Doc

開発者、設計担当者、レビュー担当者、関係チームに向けた設計書である。実現方法と採用理由、代替案、それぞれの利点や負担を説明する。進捗報告、PR番号や Jira 課題IDの台帳、チケットの代替にはしない。区分は `stock` とする。

必要な情報は次のとおりである。

- 背景
- 目標・非目標
- 制約
- 設計
- 構成とデータの流れ
- 動作
- 採用理由
- 重要な失敗時の動作
- 代替案
- 不採用理由
- 影響
- リスク
- 未解決点
- システムの到達範囲
- 手順の到達範囲
- 変更を元に戻せるか

答える問いは「どう実現し、なぜその方式か」である。PR/Jira一覧、完了率、今週やることは他の管理先へ移す。

外部の API・仕様・測定結果や別 ADR など、判断の根拠となる資料を参照する。リンクだけでは読者が結論や理由を追えないなら、必要な一文を本文に残す。設計の根拠がチケットにしかない場合は、根拠となる事実を本文へ抜き出し、未確認の点を明記する。

## RFC/技術提案

複数チーム、標準化参加者、レビュアに向けた技術提案書である。技術・運用上の提案と、広い合意が必要な論点を説明する。作業計画や実装進捗の管理には使わない。区分は `stock` とする。

必要な情報は次のとおりである。

- 問題
- 提案
- 適用範囲
- 代替案
- 影響
- 状態

答える問いは「誰に何の変更への合意を求めるか」である。合意が必要な論点を残し、レビュー依頼の宛先・期限と作業台帳は他へ移す。

## ADR

技術責任者、開発者、将来の保守者に向けた判断記録である。一つの重要な決定と、その理由・結果を説明する。詳細設計、実装進捗、作業チケットの管理には使わない。区分は `stock` とする。

必要な情報は次のとおりである。

- 背景
- 決定
- 代替案・理由
- 結果
- 判断の状態と日付

答える問いは「どの一つの判断を、なぜ採ったか」である。詳細設計の複製と実装進捗は他へ移す。

ADR の「提案・採用・廃止・置換」は判断の状態であり、実装の「未着手・作業中・完了」とは別である。判断を変える場合は旧 ADR を上書きせず、新しい ADR には、置き換える旧 ADR への参照を記す。採用/廃止/置換の日付と代替 ADR への参照は記載してよい。Design Doc のレビュー期限、PR 番号、Jira 課題ID、作業状況は、依頼文やチケット・進捗文書で管理する。設計書の本文を管理先にしない。

ADR に未決定事項を必須で載せる必要はない。判断の前提やリスクとして必要か、後続の詳細設計かを、[ADR の判断と結果を残す](#adr-の判断と結果を残す)に従って分ける。

### ADR の判断と結果を残す

一つの重要な判断について、背景、決定とその理由、結果を記す。判断の状態と、資料にある判断日も残す。節を分けるなら「背景」「決定」「結果」を基本にし、代替案と不採用理由は判断を理解するために必要な範囲で書く。一段落で揃うなら、見出しを増やさない。

「結果」には、採用による利点、負担、制約、その他の影響を含める。「結果と代償」という言い方では意味が重なる。通常の費用や運用負担を一括して「代償」と呼ばず、「DB の保存量が増える」「障害時の切替操作が必要になる」のように、何が変わるかを書く。想定される影響と、実際に確認した結果は区別する。

#### 未決定事項を扱う範囲

「未決定事項」は必須の節にしない。後続の詳細設計や作業の TODO は、それを管理する設計書や作業文書へ分ける。原資料に未決定の項目があるという理由だけで、全てを ADR に転記しない。未決定事項の見出しを消して「結果」の段落に移すだけでは、役割を分けたことにならない。既存の管理先が判断に必要なら参照し、存在しない文書やリンクは作らない。

採否を左右する未確認事項は、提案中の ADR の背景や採用条件として残す。未確認事項を消して採用済みに見せない。採用済みでも、その判断が依存する仮定や、引き受けたリスク、資料で定めた再検討条件は残す。未決定事項を独立した節で説明する必要がある場合は「結果」と分け、「代償と未決定事項」のように異なる役割を束ねない。

[Nygard の原典](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)は、結果に良い影響・悪い影響・中立の影響を含める。[MADR のテンプレート](https://adr.github.io/madr/#full-template)にも、未決定事項を必須にする指定はない。上の日本語見出しと未決定事項の振り分けは、これらを踏まえた本スキルの方針である。

## セキュリティ設計/脅威モデル

セキュリティ、開発、運用の担当者に向けた設計書である。資産、境界、脅威、対策、残余リスクを説明する。セキュリティ審査の進捗報告には使わない。区分は `stock` とする。

必要な情報は次のとおりである。

- 資産
- 境界
- 脅威
- 対策
- 対策後も残るリスク
- 責任を持つ担当者や組織

## データモデル設計

開発者、DBA（データベース管理者）、データ利用者に向けた設計書である。エンティティ、関係、整合性を定める。実行中の移行手順の管理には使わない。区分は `stock` とする。

必要な情報は次のとおりである。

- エンティティ
- 属性
- 関係
- 制約
- 変更方針

## UI 振る舞い仕様

デザイン担当者、FE（フロントエンド開発）担当者、QA（品質保証）担当者、PdM（プロダクトマネージャー）に向けた仕様書である。画面状態、操作、遷移、文言を揃える。ビジュアルデザインの好みや開発進捗の管理には使わない。区分は `stock` とする。

必要な情報は次のとおりである。

- 状態
- 操作
- 遷移
- 文言
- アクセシビリティ

## 同じ題材の最小例

架空の資料: 利用者は応答が途切れると注文を再送する。新規注文 API で同じキーの再送を24時間以内は一件として扱う。同じキーで内容が異なる場合は409を返す。既存注文の変更は対象外。設計案では利用者とキーの組を一意にし、注文とキーを同じ DB トランザクションで保存する。同内容の再送には保存済みの応答を返す。別キャッシュ案は同時更新の処理が増えるため不採用。DB の保存量が増える。判断は提案段階で、24時間後のキーの扱いは未決定。

### PRD

利用者が応答を受け取れず注文を再送しても、注文を重複させない。同じ利用者が同じキー・同じ内容で24時間以内に再送した場合、注文は一件となる。同じキーで内容が異なる場合は409を返す。既存注文の変更は対象外とする。

### Design Doc

注文と再送判定用のキーを同じ DB トランザクションで保存する。利用者とキーの組を一意にし、同時に届いた再送でも注文を一件にする。24時間以内の再送は内容を比較し、同じなら保存済みの応答、異なれば409を返す。別のキャッシュへの保存は、注文との同時更新を保証する処理が増えるため採らない。24時間後のキーの扱いは未決定である。

### ADR

状態: 提案。注文の再送による重複を防ぐため、再送判定用のキーは注文と同じ DB に保存する。両者を同じトランザクションで確定するためである。別のキャッシュは同時更新を保証する処理が増えるため採らない。DB の保存量が増える。

この ADR が扱うのは保存先の判断である。24時間後のキーの扱いは上の Design Doc に残し、ADR の必須項目にはしない。保持要件が保存先の採否を左右すると分かった場合は、その条件を ADR にも残す。
