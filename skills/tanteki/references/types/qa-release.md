# QA・リリース

## テスト計画

QA（品質保証）担当、開発者、PdM（プロダクトマネージャー）、リリース責任者に向けたテスト計画である。対象、観点、環境、終了条件を計画する。実行済み結果や日々の進捗の記録には使わない。区分は `flow` とする。

必要な情報は次のとおりである。

- 対象外
- 観点
- 環境
- データ
- 終了条件
- 役割

## テスト結果

QA、開発者、PdM、責任者に向けたテストの記録である。実施内容、結果、証跡、残課題を保存する。次の作業の正式な管理先にはしない。区分は `record` とする。

必要な情報は次のとおりである。

- 版・環境
- 範囲
- 結果
- 失敗
- 証跡
- 判定

## リリース/ロールアウト計画

開発者、SRE（信頼性エンジニアリング）担当、CS（カスタマーサポート）担当、責任者に向けた展開計画である。段階的な展開方法、監視、実施可否の判定、撤回条件を決める。プロジェクト全体の進捗報告には使わない。区分は `flow` とする。

必要な情報は次のとおりである。

- 対象
- 段階
- 監視
- 判定
- 撤回
- 連絡

## データ移行計画

開発者、DBA（データベース管理者）、運用担当に向けた移行計画である。移行と切戻しを安全に実施する。恒久的なデータ仕様の複製には使わない。区分は `flow` とする。

必要な情報は次のとおりである。

- 対象
- 前提
- 手順
- 照合
- 停止・切戻し条件

## 変更履歴（Release Notes）

利用者、CS、運用担当、開発者に向けた変更履歴である。利用者に影響する変更を知らせる。内部設計や未完了タスクの説明には使わない。区分は `record` とする。

必要な情報は次のとおりである。

- 版・日付
- 変更
- 影響
- 移行
- 注意事項

## 受け入れテスト手順書

実施者と依頼元に向けた受け入れテスト手順書である。変更が期待どおり動くことを、実行できる手順で確かめる。テストコードの設計や網羅率の議論には使わない。区分は `record` とする。

必要な情報は次のとおりである。

- 目的
- 前提条件
- シナリオごとの手順と合否判定
- 関連文書

実施者がそのまま実行できる手順で書く。シナリオごとに手順と合否判定を並べ、チェックボックスで実施の記録を残す。テストコードの設計や網羅率はここに書かない。

検証観点を表にする場合は、観点の識別子、確認内容、対応するシナリオを列に持たせる。

チェックボックスが本文の一部になるため、`record` で検査する。参照用の文書として検査すると、すべてのチェックボックスが作業進捗として指摘される。
