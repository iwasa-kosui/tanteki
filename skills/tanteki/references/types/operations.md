# 運用・障害

## 運用 Runbook

SRE（信頼性エンジニアリング）担当、オンコール担当、サポート担当に向けた運用手順書である。定型作業や障害対応を再現できるようにする。事故の原因分析や作業の進捗報告には使わない。区分は `stock` とする。

必要な情報は次のとおりである。

- 前提
- 検知
- 手順
- 確認
- 停止条件
- 連絡先

## SLI/SLO 方針

SRE、開発、PdM（プロダクトマネージャー）、責任者に向けた信頼性方針である。SLI（信頼性を測る指標）と SLO（その目標値）、測定方法、対応方針を定める。直近リリースの達成状況を日報化する文書ではない。区分は `stock` とする。

必要な情報は次のとおりである。

- 指標
- 目標
- 集計期間
- 集計から除く対象や条件
- 目標を満たさない場合の対応方針

## インシデント記録

オンコール担当、運用担当、関係チームに向けた、発生中の障害の記録である。影響、出来事の順序、対応の状況を共有する。恒久対策の設計や個人の評価には使わない。区分は `flow` とする。

必要な情報は次のとおりである。

- 影響
- 検知
- 時系列
- 対応
- 現在の状態
- 次に判断すること

## ポストモーテム

関係チーム、責任者、将来の保守者に向けた障害の振り返り記録である。影響、原因、再発防止を学べるようにする。個人を責めず、チケットの進捗の正式な管理先にはしない。区分は `record` とする。

必要な情報は次のとおりである。

- 影響
- 時系列
- 原因
- 寄与要因
- 改善策
- 対応課題への参照

ポストモーテムから対応課題へのリンクや参照は許す。ただし、対応課題の進捗・担当・期限の正式な管理先はチケット側に置く。

## 廃止/移行告知

利用者、社内利用チーム、CS（カスタマーサポート）に向けた移行告知である。旧機能や API の終了と移行先を知らせる。代替設計の全詳細や個別タスクの管理には使わない。区分は `stock` とする。

必要な情報は次のとおりである。

- 対象
- 理由
- 期限
- 影響
- 移行先
- 問い合わせ先

## 手順や記録では残すものが違う

### Runbook

実行者、開始条件、順序、期待結果、停止条件、復旧・連絡先を残す。短くしても危険な操作の条件を落とさない。

### 進捗報告を書くとき

対象期間、完了、次の作業、阻害要因、判断依頼を残す。追跡先の課題や PR を参照してよい。

### ポストモーテム

検知時刻、影響、経過、原因と寄与要因、改善策を残す。事実と仮説を分け、課題を参照してよい。

### 手順

コマンドはそのまま実行できる形で書く。山括弧で囲んだ仮の値を、未記入のまま残さない。値は変数定義にまとめ、権限の切り替えを含めて実行できる形にする。

### 報告

個人名を書かない。見解はチーム名で示す。他の案に懸念がある場合は、その案のどの性質が問題かを書く。
