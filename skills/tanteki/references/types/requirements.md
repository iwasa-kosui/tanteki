# 要求・仕様

| 種別 | 主な読者 | 目的 | 目的ではないこと | 最小内容 | 区分 |
|---|---|---|---|---|---|
| 要求仕様 | PdM、開発、QA、顧客/業務担当 | 必要な能力・制約・優先度を明文化する | 実現方式を固定する | 要求、優先度、根拠、制約、検証方法 | stock |
| ユーザーストーリー | PdM、開発、QA | 利用者の価値を実装可能な単位にする | 技術設計や進捗台帳になる | 利用者、行動、価値、受入条件 | stock |
| ユースケース | 業務担当、開発、QA | 主経路、例外、関係者、結果を記述する | 画面の見た目だけを定める | アクター、前提、基本経路、例外、結果 | stock |
| 機能仕様 | 開発、QA、PdM | 入出力、状態、ルール、エラーを実装可能にする | アーキテクチャ判断やタスク分解を行う | 入力、出力、状態、ルール、エラー、例 | stock |
| 非機能要求 | 開発、SRE、セキュリティ、QA | 性能、可用性、保守性、安全性の基準を定める | 具体的な製品や実装を無条件に選ぶ | 指標、目標値、測定方法、制約、例外 | stock |
| API 仕様 | API 利用者、開発、QA | 外部との入出力契約と互換性を定める | サーバ内部のクラス設計を説明する | エンドポイント、型、認証、エラー、互換性 | stock |
| データ/イベント仕様 | 開発、データ基盤、分析、QA | スキーマ、意味、版、保持を共有する | 業務全体の手順や分析結果を記録する | 項目、型、必須性、意味、版、保持期間 | stock |

## 仕様書の2つの形

番号を振った章で要件を並べる形と、対象ごとに設定と方針を並べる形がある。前者は機能の要件を決める文書、後者は運用や監視の設定を引くための文書になる。どちらを書くかを決めてから節を起こす。1つの文書に混ぜない。
